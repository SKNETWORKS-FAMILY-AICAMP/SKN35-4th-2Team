# 바뀐 부분과 설계 설명

3차 프로젝트와 비교해서 **무엇이 바뀌었고, 왜 이렇게 만들었는지**를 쉽게 적은 문서입니다.

---

## 1. 한 줄 요약

> 3차의 "질의응답 엔진"은 **그대로 두고**, 그 앞에 **Django 서버(back)** 와 **HTML/CSS/JS 화면(front)** 을 새로 만들었다.

식당에 비유하면 이렇습니다.

| 식당 | 우리 프로젝트 |
|---|---|
| 손님이 앉는 홀 | **front** (화면) |
| 주문서(메뉴 이름, 수량) | **API** (`/api/chat/`) |
| 주문을 받아 주방에 전달하는 직원 | **Django** (`back/chat`) |
| 요리하는 주방 | **엔진** (`back/src`, 3차 코드) |

손님(화면)은 주방이 어떻게 요리하는지 몰라도 되고, 주방(엔진)은 손님이 누구인지 몰라도 됩니다. **주문서 형식만 지키면** 됩니다.

---

## 2. 무엇이 바뀌었나

### 그대로인 것 (수정하지 않음)
`back/src/` 안의 질의응답 엔진: LangGraph, RAG(문서 검색), MCP(도구 조회), 멀티모달, DB 계층.
3차에서 이미 평가를 마친 코드라서, 건드리면 품질이 달라질 위험이 있어 **읽기만** 합니다.

### 빠진 것 (Streamlit 전용 코드)
`app/chat.py`, `app/ui_components.py`, `app/browser_auth.py`, `app/attachments.py`
Streamlit 화면과 쿠키 로그인을 위한 파일이라서 웹 서버 방식에서는 쓰지 않습니다. (`evaluation/`, `preprocessing/`도 서비스에는 필요 없어 옮기지 않았습니다.)

### 새로 만든 것
| 위치 | 역할 |
|---|---|
| `back/manage.py`, `back/config/` | Django 설정 (화면 파일 위치, 보안, 정적 파일) |
| `back/chat/views.py` | 질문을 받아 엔진을 부르고, 답변을 조각조각 돌려줌 |
| `back/chat/urls.py` | 주소 연결 (`/`, `/api/chat/`, `/api/health/`) |
| `back/chat/apps.py` | 서버가 켜질 때 모델을 미리 준비(웜업) |
| `back/chat/accounts.py` | 가입, 로그인, 로그아웃, 내 정보 (계정은 3차 DB 계층 재사용, 서명된 쿠키 세션에 user_id만 저장(DB 세션 테이블 불필요), 가입 규칙은 3차보다 엄격하게 4차에서 추가 검사) |
| `back/chat/tests.py`, `test_accounts.py` | 웹 계층 테스트 61개 |
| `back/chat/conversations.py` | 대화 목록, 불러오기, 삭제 (소유자 확인은 3차 DB 계층) |
| `front/` | 채팅 화면: 로그인·가입, 대화 목록, 마크다운 답변 (`chat.html`, `chat.css`, `chat.js`, `markdown.js`) |
| `pyproject.toml` | 의존성을 Django 중심으로 새로 정리 (Streamlit, torch 제거) |
| `.env.example`, `.gitignore` | 환경변수 목록, 올리면 안 되는 파일 목록 |

## 3. 질문 하나가 처리되는 과정

```
 사용자가 질문 입력
        │
        ▼
 ① chat.js      질문 + 이전 대화를 /api/chat/ 으로 보냄
        │
        ▼
 ② views.py     요청이 올바른지 검사 (형식, 길이, 역할)
        │
        ▼
 ③ 엔진 실행    별도 스레드에서 run_chat() 호출
        │          ├─ RAG: 공식 문서 검색 → 재정렬 → 답변
        │          ├─ MCP: 버전/릴리스 같은 실시간 정보 조회
        │          └─ 멀티모달: 이미지 분석
        │
        ▼
 ④ 스트리밍     엔진이 단계·답변 조각을 내보낼 때마다 즉시 화면으로 전달
        │
        ▼
 ⑤ chat.js      stage → 상태 문구, token → 말풍선에 이어 붙임,
                sources → 출처 목록, done → 전체 답변으로 확정
```

## 4. 설계 결정과 이유

### ① 폴더를 `front/`와 `back/`으로 나눴다
- **이유**: 팀원이 "내 파일이 어디인지" 바로 알 수 있게. 화면 담당은 `front/`, 서버 담당은 `back/`만 열면 됩니다.
- Django는 원래 한 폴더에 섞어 두는 방식이 흔하지만, 초보 팀이 헷갈리지 않도록 설정(`settings.py`)에서 화면 폴더를 `front/`로 지정했습니다.

### ② 엔진은 수정하지 않는다
- **이유**: 3차에서 평가한 품질을 보존하고, 웹 작업이 엔진을 망가뜨리지 않게.
- 서버는 `run_chat()` 함수 하나만 부릅니다. 엔진을 바꿔야 하면 팀과 먼저 상의합니다.

### ③ 답변을 한 번에 주지 않고 스트리밍(SSE)으로 준다
- **이유**: 답변 생성에 수 초가 걸리는데, 그동안 빈 화면이면 고장 난 것처럼 보입니다. 단계 문구와 글자가 바로 나타나면 기다리기 편합니다.
- **방식**: 서버가 `text/event-stream`으로 이벤트(`stage`, `token`, `sources`, `done`, `error`)를 순서대로 보냅니다. 화면은 도착하는 대로 이어 붙입니다.
- **주의**: 서버(nginx) 앞단이 응답을 모아서 보내면 스트리밍이 깨집니다. 그래서 `X-Accel-Buffering: no` 헤더와 nginx의 `proxy_buffering off` 설정이 필요합니다.

### ④ 엔진은 별도 스레드, 결과는 큐로 받는다
- **이유**: 엔진은 "다 끝나야 결과를 돌려주는" 동기 함수입니다. 그대로 부르면 서버가 끝날 때까지 아무것도 못 보냅니다.
- **방식**: 엔진을 스레드에서 돌리고, 엔진이 내보내는 단계·조각을 큐에 넣으면 서버가 꺼내서 바로 화면으로 흘려 보냅니다. (`views.py`의 `event_stream`)

### ⑤ 서버가 켜질 때 미리 준비(웜업)한다
- **이유**: 첫 질문에서 모델과 그래프를 만들면 첫 사용자만 오래 기다립니다. 서버 시작 때 한 번 준비해 두면 이후 질문이 빠릅니다.
- `migrate`, `test`, `check` 같은 관리 명령에서는 건너뜁니다. 시험용으로 끄려면 `CODECLUE_NO_WARMUP=1`.

### ⑥ 보안 기본값
| 위험 | 대응 |
|---|---|
| 남의 사이트가 대신 질문을 보냄(CSRF) | Django CSRF 검사 (쿠키 + `X-CSRFToken` 헤더). 위반 시 403 |
| 엔진 오류에서 키·경로 같은 내부 정보 노출 | 예외 내용은 화면에 보내지 않고 일반 문장만 보냄 |
| 서버가 준 글이 화면에서 코드로 실행됨(XSS) | 화면은 `textContent`로만 출력, 출처 링크는 http/https만 허용 |
| 이상한 대화 기록 삽입(예: 가짜 system 지시) | 서버가 역할을 `user`/`assistant`만 허용하고 길이를 제한 |
| 비밀값이 저장소에 올라감 | `.env`는 `.gitignore`에 있고, 예시 파일(`.env.example`)에는 값이 없음 |
| 운영 서버가 개발 모드로 실행됨 | `DJANGO_DEBUG=0`인데 `DJANGO_SECRET_KEY`가 없으면 서버가 시작되지 않음 |

### ⑦ 재정렬 모델은 ONNX int8로 서버에서 가볍게
- **이유**: 서버에 torch 같은 큰 라이브러리를 설치하지 않아도 되고, 메모리와 시작 시간이 줄어듭니다.
- 모델 파일(약 570MB)은 저장소에 올리지 않고, 변환 방법은 [README](../../README.md#6-실행-방법)에 적었습니다.

## 6. 용어 풀이

| 말 | 쉬운 뜻 |
|---|---|
| 프론트엔드 | 사용자가 보는 화면 (HTML 구조, CSS 모양, JS 동작) |
| 백엔드 | 사용자가 못 보는 서버 쪽 처리 |
| API | 화면과 서버가 주고받는 주문서 형식 |
| SSE | 서버가 답변을 조금씩 계속 보내 주는 방식 |
| RAG | 질문과 관련된 문서를 먼저 찾아서, 그 내용을 근거로 답하는 방식 |
| MCP | AI가 외부 도구(버전 조회 등)를 쓰게 해 주는 규격 |
| 웜업 | 서버 시작 때 모델을 미리 준비해 두는 것 |
| CSRF | 남의 사이트가 내 권한으로 몰래 요청을 보내는 공격 |
